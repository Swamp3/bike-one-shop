TriCon Web Interface Reference

TriCon is TriData's SOAP web service that connects a TriBike ERP installation to an external web shop. It exchanges catalog, stock, customer, order and document data as XML over SOAP — 44 functions in total, analyzed here from the official documentation and organized for building a shop integration on top of it.

Vendor support: +49 911 247675-0 · support@tridata.de — for your IdentifyGuid and the WSDL URL for your instance.

Protocol & authentication

Transport

SOAP 1.1/1.2 over HTTP(S), payloads as XML. The exact request/response shapes for your TriCon instance are published as a WSDL — open the web service's own URL in a browser to get it (append ?wsdl or use the URL TriData gives you).

Every call in this reference is described by its inner parameters and result fields; the outer SOAP envelope follows the standard WSDL-generated shape.

IdentifyGuid

Your authentication token. It is sent as a parameter on every single request — there is no separate login call. TriData issues it during project setup.

Store it as a server-side secret in the shop backend; never expose it to the browser.

Data flow

Two independent directions of traffic, both authenticated with the same IdentifyGuid.

TriBike → web interface → shop (Download)
  • Items — every item flagged for web use, with retail/purchase prices and category assignments.
  • Color/size variants — only if the color/size module is active; otherwise each variant is its own separate item in TriBike.
  • Customers — existing TriBike customers, mainly for B2B shops.
  • Stock — pushed to the interface automatically whenever stock changes in TriBike.
  • Item images — the interface serves back an image URL path.
  • Invoices — exported as PDFs via an ftp path.
  • Order states — updated automatically as TriBike processes an order.
Shop → web interface (Upload)
  • Orders — customer, delivery address, delivery term, shipping cost, prices, payment and every order line, in one call.
  • Customers — can be uploaded standalone, e.g. when someone registers without ordering.

TriBike module dependencies

Which functions apply — and how — depends on how the connected TriBike system is configured.

Color/size module (Größen Farben Modul)

When active, variants are modeled as color/size combinations under a parent item — fetch them with DownloadGrFaKombi, related to their parent via ArtikelGrFaKombi.Artikel. Use the *ColorSize* stock functions instead of the plain stock functions. When inactive, each variant is simply its own separate item in TriBike — talk to TriData support if that makes variant management impractical for your shop.

Branches (Filialen)

One interface for all branches: one "main" branch is directly connected; manual upload/download only happens there, but stock covers every branch (use the branch-aware stock functions). You can create orders for other branches by setting Filialname in the Order object — the main branch downloads them and routes them to the right branch.

One interface per branch (or single-branch selling): don't use the branch stock functions, and leave Filialname unset on orders.

Building the shop sync

A practical call order for wiring a new shop up to this interface, derived from the function set below.

1

Load reference/lookup tables once

DownloadKundengruppen, DownloadFarbe, DownloadGroesse — small, mostly-static tables your catalog and pricing will join against.

2

Full catalog import

DownloadArtikelAll for every item, then DownloadGrFaKombi for variants if the color/size module is active. Key off ArtikelID; use I_VKnetto/I_VKbrutto as the web-facing price, not VKnetto.

3

Images and pricing tiers

DownloadArtikelbild for product images; DownloadArtikelKundengruppenPreis/DownloadArtikelKundenPreis if you're running B2B tiered or negotiated pricing.

4

Stock import, then poll deltas

DownloadStock (or the ColorSize/Branch variants that match your setup) for the initial load, then the matching *Delta function on a schedule using LastChange — TriBike pushes stock changes to the interface the moment they happen, so short polling intervals are safe.

5

Incremental catalog sync

Switch from DownloadArtikelAll to DownloadArtikel with LastChange; use DownloadArtikelNrAll / DownloadGrFaKombiBarcodeAll periodically to detect items deleted on the TriBike side.

6

Checkout: UploadOrder

Send Customer + Order + OrderItemsList together on every order — even for a returning customer. Always set a unique WebShopOrderID outside TriBike's own number range; it's the only way to relate the order back later.

7

Post-checkout status

Poll DownloadOrderStateByOrder (or ByCustomer for an account page) to reflect TriBike's fulfillment state in the shop; use UploadOrderChangeBezahlt once payment settles and UploadOrderChangeStorno for cancellations.

8

Documents

DownloadRechnungen / DownloadGutschriften (and their ByCustomer/ByOrder/ByInvoice variants) to surface invoice and credit-note PDFs in an account area.

Before building: confirm with TriData support whether the color/size module and branches are active on the target TriBike instance — both change which functions apply and how several fields (stock, Filialname) behave.

Upload data formats

The four objects TriCon expects on upload, field by field. Order and OrderItems are also embedded inside UploadOrder; CustomerExt is shared by UploadCustomer and the Customer block of UploadOrder.

Key identifiers, at a glance

FieldMeaning
ArtikelIDPrimary key for an item — use this for identification wherever available.
ArtikelnummerSecondary/display item number. On order upload, only the first 20 characters are used by TriBike.
ArtikelGrFaKombiIDPrimary key for one color/size variant of an item.
GrFaBoolean on the item — true means it has color/size variants to look up via DownloadGrFaKombi.
I_VKnetto / I_VKbruttoNet/gross price configured specifically for web use — prefer these over VKnetto/VKbrutto for shop display.
WebShopOrderIDYour own order number, set on UploadOrder. Required for order-state polling and the UploadOrderChange* functions to work at all.
KundennummerTriBike's customer number — set it explicitly only with a number range outside TriBike's own.
UserIDMandatory customer field, normally the email address — TriData's primary match key for de-duplicating customers.
FilialnameBranch name — only relevant on multi-branch TriBike setups; leave unset otherwise.
LastChangeThe delta-sync parameter across nearly every Download function — pass the timestamp of your last successful sync.
